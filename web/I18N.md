# UI localization

Chinese (`zh-CN`) is the default. English (`en`) is an explicit choice stored in
`localStorage` under `artex.ui-locale`. The selector is on login/setup pages and
in the expanded navigation sidebar, including its mobile drawer. Selecting a
language also saves the instance-wide Agent output language through the existing
settings API (`output_language`: `zh` or `en`). There is one selector for both.

English covers auth/navigation, Dashboard, Tasks and every detail tab, Chat,
Workspace, Assets, Findings/cases, traffic/evidence, Repeater, Schedules, Asset
Sync, Agents/editor, LLM profiles, MCP, Skills, Tools, Notifications,
interception/approvals, logs controls and Settings, including updates and proxy
pools/reconnect controls. Nested dialogs, validation, empty/loading states and
unchanged bundled Agent/rule labels translate at the display boundary.

Stored prompts, model-facing tool schemas/descriptions, custom names, historical
user/model content, saved reports, raw HTTP/evidence, logs and backend error
details remain verbatim. Runtime prompts receive an English output directive
when English is selected, covering role replies and natural-language tool
arguments, side-question replies, wrap-up, titles, graph compaction and credential processing. Technical
identifiers and raw evidence stay unchanged. The default Chinese path is unchanged.
The Next development authentication gate runs before the client locale is loaded;
its server diagnostics also remain unchanged. Prompt directives guide model
output; they do not guarantee language compliance or control reasoning blocks.

Command rules expose no bundled/custom marker. Their exact original bundled
names receive translated display labels; a custom rule using that same name is
indistinguishable. Editors and API values retain the original text.

## Implementation

`src/i18n/provider.tsx` wraps the application in `NextIntlClientProvider`. Messages
live in `messages/zh-CN.json` and `messages/en.json`. This uses client-side locale
state without locale routes, middleware changes or a server-side locale cookie,
so the existing static export and embedded Go frontend continue to work.

The static HTML and initial hydration render are Chinese. A saved choice is
restored after hydration; a brief Chinese render on reload is accepted. Invalid
saved locales fall back to Chinese. When storage is unavailable, selection still
works in memory. Changing language updates context without remounting children.

Locale selection does not alter timezone, schedules, authentication, API paths,
stored prompt versions, historical content or raw HTTP/evidence. Existing clock rendering remains
unchanged. The intl provider's timezone is restored from the browser independently
of language. Shared date/number formatting follows the UI locale; schedule
timezone selection and date/time wire values retain upstream semantics.

The UI switches immediately. If the settings save fails, it keeps the selected
locale and shows an error with Retry; Agent output language remains at the last
successful save. The selector is disabled during a save to prevent overlapping
writes. Login/setup selections are pending until authentication succeeds;
`sessionStorage` carries the pending choice across the login reload. Restoring
an old UI preference alone does not write backend settings. Separate browsers
retain their UI locales; the latest successful language save controls output
across the instance. Changes apply when runtime prompts are next assembled;
already-running workers can finish using their previous language.

Generated origin-node labels are localized from their description/goal fields
only when the summary matches the backend's exact generated wrapper. Custom
summaries and stored node payloads remain unchanged. Planner round markers and
a few fixed system notices use the same exact-match rule
(`src/lib/system-activity.ts`). The task Report tab renders English labels when
`output_language=en`.

Known backend errors (`apiErrors`) are the Chinese `writeErr` texts in
`server/*.go`. `ApiError` localizes an exact template match for English; values
after a fixed prefix or in format arguments stay verbatim, and unknown errors
are unchanged. `ApiError.raw` keeps the server text for code that matches it.
`npm run test:i18n` fails when a catalog entry no longer matches the Go source;
add new `writeErr` texts to both catalogs.

## Adding translations

1. Use a semantic namespace and key in both catalogs, such as `login.title`.
2. Use `useTranslations("login")` inside a client component and render `t("title")`.
   Derive translated navigation metadata at render time, not module initialization.
3. Use ICU arguments for values, and `t.rich` for markup. Preserve argument names
   and types between languages. Do not translate user or backend content by
   matching rendered strings.
4. Store local validation error keys in state so visible errors follow language
   changes. Keep unknown backend details verbatim. Avoid locale dependencies in
   data-fetching effects or locale keys that remount interactive components.
5. Check Chinese wording against current source and review English for meaning;
   matching catalog keys cannot detect stale translations by itself.
6. Use direct verbs for actions and sentence case for ordinary controls. Prefer
   "Sign in", "LLM profile", "Objectives", "Worker", "Tool executions", "LLM
   recordings", "Approval records" and "Asset blocking" in their corresponding
   contexts. Preserve conditions, limits, fallback order and side effects.
7. For corresponding shared screens, consult the pinned ScopeWeaver wording
   below. Current ARTEX meaning takes precedence. Translate whole messages with
   ICU arguments rather than joining fragments; preserve custom/edited metadata.

## Verification

From `web/`, with Node.js 22:

```bash
npm ci
npm run i18n:check
npm run test:i18n
npm run i18n:inventory
npm run build:static
npx playwright install chromium
npm run test:i18n:browser
```

The build includes TypeScript validation. Browser tests serve the actual static
export on loopback and mock API responses; they do not require a backend or real
credentials. They cover locale persistence, auth/navigation, retained drafts,
streams and raw content, unchanged API values, schedules/timezones, Asset Sync,
Repeater, Findings, Settings and mobile controls. They do not exercise live
backend auth, external LLM execution, real proxy connectivity or every dialog.

The AST inventory lists Chinese candidates for manual classification. Strict
checks cover the completed screens and reviewed metadata/protocol exceptions in
`scripts/i18n.test.mjs` and `scripts/i18n-coverage.json`. Stored seed names and
model-facing mention tokens are intentional exceptions. Inspect English layouts
in both themes and at narrow widths; do not shorten accurate messages to conceal
overflow.

After both catalogs exist in git history, optionally run
`npm run i18n:check -- --base <commit>` to identify changed Chinese entries whose
English wording has not changed. This reports review candidates, not failures.

## Translation attribution

English wording for corresponding shared screens and terms is adapted
from [ScopeWeaver](https://github.com/cskwork/scopeweaver/tree/407c8bbdb7855e683b2be8ffb288dd7776c835ac)
(`web/src/i18n/messages/{interface,common,settings,app,english}.ts`) with current
ARTEX wording and behavior taking precedence. The wider translation work also
consulted [artex-global](https://github.com/jiwoochris/artex-global/tree/fdfb7a17b7da5e2de716c0e98475ec77a41c64c6)
for next-intl integration patterns and compatible translations, including Asset
Sync. The language selector follows ScopeWeaver's bordered native select with a
Languages icon. Newer workflows absent from the pinned references, including
Repeater, are translated against current ARTEX. Credit belongs to those projects' authors and
contributors. Both projects and ARTEX use AGPL-3.0; the root LICENSE continues to
apply. The coupled selector and runtime language directive approach follows
artex-global's `agent/prompt.go`, `agent/outputlang.go`, role/wrap-up builders and
Settings language handler at the pinned revision. This implementation uses the
existing ARTEX settings resolver pattern, retains the Chinese default, and also
covers current standalone title/compaction/credential calls. Prompt bodies and
backend seed mutations are not imported. Chinese terms and restrictions are preserved.
