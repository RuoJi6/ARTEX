# UI localization

Chinese (`zh-CN`) is the default. English (`en`) is an explicit choice stored in
`localStorage` under `artex.ui-locale`. The selector is on login/setup pages and
in the expanded navigation sidebar, including its mobile drawer.

This first contribution covers login and terms, initial password setup, account
menus/password changes, sidebar navigation/search, layout preferences, theme
controls, header version/update labels and shared dialog/sidebar controls.
Feature page contents, proxy diagnostics and backend errors remain unchanged.
English is therefore partial; further screens can be contributed incrementally.

## Implementation

`src/i18n/provider.tsx` wraps the application in `NextIntlClientProvider`. Messages
live in `messages/zh-CN.json` and `messages/en.json`. This uses client-side locale
state without locale routes, middleware changes or a server-side locale cookie,
so the existing static export and embedded Go frontend continue to work.

The static HTML and initial hydration render are Chinese. A saved choice is
restored after hydration; a brief Chinese render on reload is accepted. Invalid
saved locales fall back to Chinese. When storage is unavailable, selection still
works in memory. Changing language updates context without remounting children.

Locale selection does not alter timezone, schedules, authentication, API paths,
prompts, stored content or raw HTTP/evidence. Existing clock rendering remains
unchanged. The intl provider's timezone is restored from the browser independently
of language; this contribution introduces no date-formatting calls.

## Adding translations

1. Use a semantic namespace and key in both catalogs, such as `login.title`.
2. Use `useTranslations("login")` inside a client component and render `t("title")`.
   Derive translated navigation metadata at render time, not module initialization.
3. Use ICU arguments for values, and `t.rich` for markup. Preserve argument names
   and types between languages. Do not translate user or backend content by
   matching rendered strings.
4. Store local validation error keys in state so visible errors follow language
   changes. Keep unknown backend details verbatim. Avoid locale dependencies in
   data-fetching effects or locale keys that remount interactive components.
5. Check Chinese wording against current source and review English for meaning;
   matching catalog keys cannot detect stale translations by itself.

## Verification

From `web/`, with Node.js 22:

```bash
npm ci
npm run i18n:check
npm run test:i18n
npm run build:static
npx playwright install chromium
npm run test:i18n:browser
```

The build includes TypeScript validation. Browser tests serve the actual static
export on loopback and mock API responses; they do not require a backend or real
credentials. They cover locale persistence, auth drafts/errors, navigation,
mobile controls and clock invariance. They do not test live backend auth.

After both catalogs exist in git history, optionally run
`npm run i18n:check -- --base <commit>` to identify changed Chinese entries whose
English wording has not changed. This reports review candidates, not failures.
